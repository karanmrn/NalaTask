1. The brief, decoded

NALA moves money from UK/US/EU to Africa and Asia. Three systems land in Snowflake RAW. The job: a dbt layer that finance, ops, fincrime and growth can trust, plus a semantic layer so Hex reads metrics instead of tables.

Source 1: Payments backend

Postgres, StreamServe CDC, near-real-time. 9 tables. 15M transactions, 20M payout attempts. Users, accounts, transactions, collections, disbursements, attempts, recipients, recipient accounts, ops tasks.

Source 2: Fincrime service

Postgres, StreamServe CDC. 5 tables. 30M rule executions. Rules (versioned), workflows, workflow executions, rule executions, formal reviews. Triggers tasks in Source 1.

Source 3: Amplitude

Fivetran daily batch ~06:00 UTC. 1 table, 100M events. Exploratory only: onboarding funnel for growth.

3. Grain first: the one idea that prevents double counting

Grain means what one row represents. One transaction can have two attempts and three reviews. Join both and you get six rows for one amount. DISTINCT on the amount is not a fix: two different transactions can share an amount.

4. The pipeline: what each layer buys

Production vs exploratory, three differences

  • production selector never includes the Amplitude branch; separate job.
  • Exploratory tests are severity: warn; production tests block.
  • Contracts enforced only on marts/.

Materialization rule of thumb

  • No logic, no storage: staging and intermediate are views.
  • Big and mutable: incremental merge with a lookback (3 large facts).
  • Small or cheap to recompute: table (aggs, dims, reviews, tasks).
  • Needs history the source throws away: snapshot.

5. Six decisions that changed between the GPT draft and the submission

Each card is a likely interview question. The last line of each is the sentence to say.

CDC: dedupe the change log

Draft: assume a merged current-state replica, refuse to dedupe ("no ordering column supplied").

Now: assume append-only log with _cdc_lsn, _cdc_operation, _cdc_loaded_at. cdc_current_rows() keeps the highest LSN per key and drops DELETE. One variable flips to pass-through. Synthetic data proves it: 402 log rows become 399 current rows.

"Staging owns the CDC contract. Downstream never deduplicates again."

Incremental on updated_at, with a lookback

Draft: full rebuild of 15M/20M/30M-row tables every run; one incremental path shipped disabled.

Now: merge on the natural key, filter updated_at >= max(updated_at) - 3 days. Creation-date filters miss an old attempt that changes today; update-date filters catch it. Full refresh stays one flag away.

"Filter on when the row changed, not when it was born."

completed_at from a snapshot

Draft: "no completed_at supplied", so finance volume was on creation date.

Now: snap_transaction_state records every state transition dbt sees. completed_at = first COMPLETED transition, else updated_at when the current state is COMPLETED (the brief defines updated_at as the last state change). Volume on completed_date; success rate on creation cohort.

"Two clocks, two columns, never mixed in one aggregate."

USD via as-of rate, not exchange_rate

Draft: exact-date join to an approved rate table; any weekend nulled the whole day.

Now: latest rate on or before the transaction date, max 7 days old, fx_rate_age_days exposed. Still null (not partial) when no rate exists. exchange_rate is sent-to-received (GBP to KES), never USD.

"The supplied exchange rate answers a different question."

Denominators are the brief's, not the textbook's

Provider success = completed / all attempts, pending included (1 of 3 is 33%, not 50%). False positive rate = FALSE_POSITIVE / all formal reviews, INCONCLUSIVE and repeats included. Rates are sums divided by sums so 90/100 and 1/10 give 82.7%, not 50%.

"A different denominator is a different metric with a different name."

Task linkage is inferred, and says so

No key from task to workflow execution. Match on the same entity, a task-producing action, and a 60-minute window. One candidate = UNIQUE_INFERRED; two = AMBIGUOUS; none = UNMATCHED. Every task stays counted. The real fix is upstream: emit workflow_execution_id.

"Nearest is not cause. I keep the ambiguity visible and ask for the key."

9. How it was built with AI

  • Pass 1
    ChatGPT (GPT-6): first draft. Brief in, full project out: 15 stagings, 9 marts, semantic YAML, docs. Good grains and denominators. Could not run dbt, so it built a SQLite harness and wrote hedged prose. Never parsed.
  • Review
    Claude Code: audit against the brief. Found: contract type mismatches, array_contains on a VARIANT, mart reading source() directly, no CDC dedupe, no incremental plan, finance on creation date, exact-date FX join, disclaimers in the candidate's name.
  • Make it real
    Fresh git repo, uv, dbt 1.12. Adapter-dispatch macros so the same SQL runs on DuckDB and Snowflake. Synthetic RAW generator with deliberate edge cases (CDC update and delete, exactly 24h latency, repeat reviews, retired rule version, shared device). dbt build green.
  • Upgrade
    Senior-level changes. CDC macro, incremental merge, snapshot, as-of FX, finance volume on completion date, dims, freshness, MCP config, sqlfluff, CI. Deleted the harness and every disclaimer.
  • Docs
    Architecture, README, prompt log rewritten in first person with one assumptions table. This explainer.
What the human did: chose grains and denominators, decided the two finance clocks, rejected the Snowflake trial (the brief says "need not be runnable"; DuckDB plus dbt parse --target prod covers the risk), rejected the harness, read every model once before sending.

10. Interview drill

Two dashboards disagree: 90% vs 82% payout success. Go.

First question: what is one row? 90 successful transfers out of 100 versus 90 successful attempts out of 110 are both right. Then: same date axis (creation vs completion)? same state cutoff? pending excluded on one? retries counted? cache age? Reproduce both numbers from fct_disbursement_attempts and fct_transactions, diff by key on the day they diverge, then fix the definition in the semantic layer so both read the same metric.

Why not incremental on every model?

Views cost nothing to keep fresh. Aggregates recompute from facts in seconds. Only the three large mutable facts pay for merge. Incremental needs a change signal I trust: updated_at plus a lookback. Tables without an update column (users) stay full rebuild until the CDC checkpoint is exposed.

What if StreamServe already merges to current state?

cdc_landing_mode: current_state. The macro becomes select *. Nothing else changes. What I lose is the delete signal and the ability to see intermediate states between runs; the snapshot still captures what dbt sees.

Why is the false positive rate not FP/(FP+TN)?

Because the brief defines it as FALSE_POSITIVE reviews over all reviews, and the source has no true negatives (rules that passed are not reviewed). A classifier-style rate would need a different denominator and a different name.

Why is Amplitude not in the production job?

100M rows, daily batch, no production consumer, and two contracts unconfirmed (final KYC step, identity). It has its own selector, its own job triggered by the Fivetran webhook, and warn-only tests. Promotion criteria are written in the architecture doc.

How would an AI agent work safely in this repo?

AGENTS.md is the contract: state the grain, reproduce before changing, write the failing test, run make build, attach evidence. .mcp.json gives it dbt and Snowflake tools with a read-only role and an XS warehouse. docs/agent_evaluation.md holds nine golden tasks, including a prompt-injection case in a review comment.

What would you ask NALA first?

StreamServe landing shape and metadata columns. Whether outgoing P2P counts as commercial volume. Who owns the USD rate feed. Whether tasks can carry workflow_execution_id. Which KYC event means "done".
